# Add a route handler (Next.js 16)

Follow these steps in order. Write the SC-PREFLIGHT note first: the route folder and its existing `route.ts`; the shared function the handler should call (a loader in `data.ts`, a `*.service.ts` function an action already uses); `src/shared/http/` (problem details, the JSON body reader); the page shape (`src/shared/pagination.ts`); and the request logging skill's `withRouteLogging`. Reuse what exists; never add a second problem format, body reader or page shape.

Route handlers are for clients other than the app's own pages: a mobile app, another service, a webhook. The app's own forms call server actions (`stackcrew-next-server-action`) and its pages load data in Server Components (`stackcrew-next-feature-page`). The example is `/api/v1/kyc-registrations`: `GET` a page of the tenant's registrations (reviewers), `POST` the caller's own registration.

## 2. The handler

```ts
// in route.ts: the exported method, wrapped with the file's path template
export const POST = withRouteLogging('/api/v1/kyc-registrations', async (req: NextRequest) => {
  const body = await readJsonBody(req);
  if (!body.ok) {
    return body.response;
  }
  const result = await submitKycRegistration(body.value);
  return result.ok ? NextResponse.json<KycRegistrationDto>(result.data, { status: HTTP_STATUS.CREATED }) : problemForRefusal(result.error);
});
```

- Every exported method is wrapped: `withRouteLogging('<the file path template>', handler)`. The route argument is the template (`/api/v1/kyc-registrations/[id]`), never the requested path, so the log stays low-cardinality. Type the second argument as `RouteContext<'/api/v1/kyc-registrations/[id]'>` for a dynamic segment (`const { id } = await ctx.params`); `RouteContext` is generated by `next typegen` (or a build), so run it before `tsc` in CI.
- The handler adapts HTTP to a shared function and back: parse the transport input, call the function, map its `ActionResult` to a status. The caller check (`getRequestContext()`, which calls `auth()`), the role, the zod schema and the write live in that function, shared with the server action or the page loader. The shared function is never wrapped; wrap only the exports, or a call would write two lines.
- When a handler has no shared function, it does the same in the same order: `getRequestContext()` (no user → 401, no tenant or role → 403), then zod `safeParse` of the body or query (→ 400 with `errors`), then the work.
- Input: the body through `readJsonBody` (not JSON → 415, malformed → 400), parsed by the zod schema; the query with `Object.fromEntries(req.nextUrl.searchParams)` and a zod schema (`pageQuerySchema`), strictly: a bad value is a 400 naming the field, never a silent default. Path params are validated too (`z.string().uuid()` for an id). Unknown body keys are stripped; the user, the tenant and audit fields come from the session and the subscribers.
- Output: `NextResponse.json<Dto>(dto, { status })` with a DTO or a `PageDto` of DTOs, never an entity. `201` for a create, `200` for a read, `204` (`new Response(null, { status: 204 })`) for a delete.
- A wrapped GET reads the session, so it is dynamic (`ƒ` in the build output); nothing user-specific is cached.

## 3. Errors (RFC 7807)

Every refusal answers `application/problem+json` with `type: 'about:blank'`, `title` (the status text), `status`, a constant `detail` and, for validation, `errors: [{ field, messages }]`: the shape of the NestJS `AllExceptionsFilter`, so clients of both stacks parse one format.

- `problemForRefusal(result.error)` maps the shared function's code with `ACTION_ERROR_STATUS`: `VALIDATION` 400 (with `errors`), `UNAUTHENTICATED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409. The action's log line uses the same table.
- `detail` and the field messages are constant text (`ProblemText`, the schema's catalog): never an exception message, a value from the request, a stack trace or a provider's words. zod 3 quotes a bad enum value in its default message; schemas give enums an `errorMap`.
- Another tenant's row is not found (404), exactly like a missing one: the tenant repository returns `null`. A handler that reads across tenants with `runCrossTenant` catches `CrossTenantDeniedError` with `notFoundIfCrossTenantDenied(failure)`, which answers 404 and rethrows anything else.
- An unexpected error is not caught: `withRouteLogging` logs it as a 500 with its class, `onRequestError` logs its stack and digest, and Next.js answers 500 without a body. Never answer a 500 with the message.
- `redirect()` and `notFound()` work in a route handler too (the wrapper logs them at their status), but an API answers a problem instead.

## 4. Logging

`withRouteLogging` writes the one `http_in` line: method, route template, status, both bodies through the shared masker, the caller's `userId` and `tenantId`. The handler and the shared function never log a body. The line is written once both body copies are read, after the response has gone.

## 5. Safety

- Authorization is checked per request in the shared function or the handler; `proxy.ts` is not an authorization check.
- CORS: answer only the origins the API serves (an `OPTIONS` export and the response headers), never `*` with credentials.
- Set a body size limit at the edge (the reverse proxy or the platform): route handlers have no default limit.
- A non-idempotent POST that creates a resource or moves money takes an `Idempotency-Key` header (a constant name) and stores the key with the result in the same transaction. The example needs none: its unique constraint makes a repeat a 409.

## 6. Tests

`stackcrew-nextjs-testing` is the full procedure. A route handler is a function: call it with `new NextRequest(url, init)` and a context (`{ params: Promise.resolve({ id }) }`), with only `next/headers`, `auth()`, `next/cache` and the repository mocked. `route.spec.ts` covers:

- `POST` 201 with exactly the DTO keys, the applicant and tenant from the session whatever the body says, and one `http_in` line with `"idNumber":"***"`;
- 401 without a session and 403 without the role, as problem details with `content-type: application/problem+json`;
- 415 for a form body, 400 for malformed JSON, 400 with `errors` for schema violations, never quoting the input; 409 for a repeat;
- `GET` 200 with a page and the repository's `take`/`skip`; 400 for a size over the maximum; 403 for another role.

## Do not

- Do not leave a method unwrapped, wrap one twice, or call a wrapped server action from a handler.
- Do not answer `{ error: string }`, an exception message, a stack trace or an entity; use the problem helpers and DTOs.
- Do not take the user or the tenant from the body, a header or a query parameter.
- Do not catch every error to answer 500 yourself: the wrapper and `onRequestError` must see it.
- Do not hardcode statuses, header names or texts in handlers; use `HTTP_STATUS`, `ProblemText` and constants.
